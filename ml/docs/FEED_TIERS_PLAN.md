# План: двухуровневая лента с заранее объявленным порогом

Дата: 2026-10-23. Основание: ручная разметка 210 пар real (`ml/eval/review_real.md`, `ml/eval/review_real_2.md`),
разбор в `ml/eval/analysis.md`, разделы «Ручная проверка разметки реальных новостей» и «Ручная разметка, партия 2».

## Цель

Основная лента показывает только уверенные материалы; пограничные уходят в блок «может быть интересно», а не теряются.
Порог основной ленты (0,40) объявляется заранее и один раз проверяется на свежих данных (real2) с ручной разметкой.

Почему так, а не просто поднять порог:
- руководителю важнее не засорять ленту, чем ничего не пропустить: по ручной разметке при пороге 0,30 из показанного
  нужно 46%, при 0,40 — 65%;
- твёрдый срез на 0,40 теряет часть нужного (полнота 86% → 71%); блок «может быть» её сохраняет;
- 0,40 подобран на тех же 210 парах, где нужных всего 28, поэтому без проверки на свежих данных он не доказан.

Платное в плане только разметка real2 (~65–75 руб.). Остальное без вызовов LLM.

| Этап | Что | Время | Расход |
|---|---|---|---|
| 1 | Два уровня в ленте (код, схема, API, тесты) | ~2 ч | 0 |

## Этап 1. Два уровня в ленте

**`ml/ranking/ranker.py`**
- Новая константа `MAIN_SCORE = 0.40` (переопределяется `ML_FEED_MAIN_SCORE`) — порог на личный скор `Scored.personal`,
  отдельный от `MIN_SCORE`. Поднимать `MIN_SCORE` бесполезно: в режиме с моделью личный скор нормируется на него же
  (`blend_scores`), и замена ничего не изменит.
- Уровень материала:
  - `main` — личный скор от 0,40 или событие прямо в отрасли компании (совпадение ОКВЭД, `in_sector`);
  - `maybe` — личный скор от 0,30 до 0,40;
  - ниже 0,30 — отсев, как сейчас.
- Макрособытие без зацепки в профиле (компания попала в ленту только по полу `ECONOMY_MIN_IMPORTANCE`): по умолчанию
  `maybe`. Ручная разметка real и ручной срез v2 такие пары чаще всего считают ненужными. Вариант «всегда `main`»
  проверяется на этапе 4.
- `rank()` и `feed()` возвращают сначала `main` в порядке ленты, затем `maybe`.
- Отдельные лимиты: `limit` для основной ленты (20) и `maybe_limit` (10).
- У `maybe` первой причиной идёт «слабая связь с профилем», чтобы фронт мог показать это пользователю.

**`ml/schemas.py`**
- `FeedEntry.tier: Literal["main", "maybe"] = "main"` — поле добавляется со значением по умолчанию, старые клиенты не ломаются.
- `Feed.maybe_count: int = 0` для счётчика блока.
- Изменение контракта сообщить бэкенду и фронту: поля новые, старые не меняются.

**`ml/api.py`, `ml/server.py`**
- `get_ranked_feed(..., tier="all")` и `GET /companies/{id}/feed?tier=main|all`; по умолчанию `all`.

**`ml/precompute.py`**
- Карточки для демо считаются только для `main`.

**Тесты (`ml/tests`)**
- скор 0,45 → `main`, 0,35 → `maybe`, 0,25 → отсев;
- событие в отрасли компании всегда `main`; макро без зацепки → `maybe`;
- порядок: сначала `main`, затем `maybe`; лимиты соблюдаются;
- без поля `tier` схема по умолчанию даёт `main`;
- параметр `tier` в API.

## Этап 2. Метрики по уровням

**`ml/ranking/pair_model.py` (`metrics`, `cross_val`), `ml/eval/run_eval.py` (отчёт ленты)**
- основная лента: precision, recall, F1, precision@5;
- оба уровня вместе: recall (сколько нужного не потеряно);
- доля нужного в `maybe` (не прячем ли туда важное);
- F0.5 основной ленты (точность весит вдвое больше полноты).

**Метрики против человека** (`ml/eval/label_review_real.py`, новая функция)
- по всем парам с `source=human`: точность основной ленты, полнота обоих уровней, доля нужного в первой пятёрке;
- модель — только внефолдовые предсказания по дням, как в CV.

**`ml/eval/final_eval.py`**
- метрики по уровням для вариантов «прежняя», «правила», «модель+правила»;
- если для real2 есть ручная разметка — отдельный раздел «против человека».

## Этап 3. Объявить точку заранее

Записать в `ml/eval/PROTOCOL.md` до заморозки real2:
- пороги: основная лента от 0,40, «может быть» от 0,30; событие в отрасли всегда `main`; макро без зацепки — `maybe`;
- главная метрика: точность основной ленты против человека; ограничение: полнота обоих уровней против человека;
- критерий успеха на real2: точность основной ленты не ниже 60% при полноте обоих уровней не ниже 80%
  (ориентиры по 210 парам dev: 65% и 86%);
- после просмотра результатов real2 пороги не меняются; если поменяли — итоговая проверка на следующем наборе (real3).

Закоммитить, чтобы дата фиксации была видна в истории.

## Этап 4. Проверка на данных разработки

- CV по 7 дням real и по v2: метрики этапа 2 для порогов 0,35 / 0,40 / 0,45 и двух вариантов размещения макро без зацепки;
- 210 ручных пар (внефолдово): ожидание — около 65% нужного в основной ленте и 86% полноты обоих уровней;
- ручной срез v2 (9 компаний): основная лента не хуже прежней ленты сверх допуска (`pair_model.TOL_*`);
- если 0,40 явно проигрывает соседним порогам, менять объявленную точку до заморозки real2, а не после.

## Этап 5. Итоговая проверка на real2

1. Заморозка: `make real2-freeze START=2026-10-23 ASOF=<дата>` (около 100 новостей из пула).
2. Машинная разметка: `make real2-label ASOF=<дата>`.
3. Ручная разметка: добавить в `ml/eval/label_review_real.py` параметр `--set real2` (файлы `labels_real2.jsonl`,
   `review_real2_<n>.md`), затем 150 случайных пар с тем же чек-листом критериев. Размечать до просмотра результатов ленты.
4. Один прогон: `make real2-eval ASOF=<дата>` — метрики по уровням против машинной и ручной разметки, парный bootstrap
   против прежней ленты.
5. Решение по объявленному критерию: выполнен — двухуровневая лента остаётся; не выполнен — записать почему, вернуть
   один уровень с порогом 0,30, новые пороги проверять на real3.

## Этап 6. Калибровка по ручной разметке

- Задача: модель учится на машинной разметке, а она мягче человека (на случайных парах «релевантно» 15% против 8%),
  поэтому вероятности модели смещены.
- По ручным парам и внефолдовым скорам подобрать перевод «скор → вероятность, что человек сочтёт нужным». Нужных пар
  пока 28, поэтому функция из двух параметров (Platt), а не гибкая (isotonic). Параметры — в `pair_model.json`
  (`calibration: {a, b}`).
- Пороги в понятных величинах: основная лента при вероятности от 0,5, «может быть» — от 0,25.
- Проверка: вложенная CV по дням, сравнение с фиксированным 0,40. Переход на калибровку — только если она лучше на real2
  или на следующем наборе, не на dev.
- Каждая новая партия ручной разметки пополняет калибровку; при росте данных — переход к гибкой калибровке.

## Риски

- Мало нужных пар (28 на dev): точность оценки порога около ±10 п.п.; real2 с ручной разметкой это сузит.
- Изменение контракта: поле добавляется со значением по умолчанию и старое не ломает, но фронту нужно показать второй блок.
- Один разметчик: его строгость становится эталоном. Желательно, чтобы 30–50 пар real2 независимо разметил второй
  человек — это покажет, насколько оценка воспроизводима.
