# ML / Prompt-engineering: спецификация и эталонный результат

Кейс: «Альфа Хак. Новостная аналитика для принятия бизнес-решений» (Альфа-Банк x Changellenge).
Этот документ описывает зону ответственности ML/prompt-инженера и то, как выглядит идеально выполненная работа. Его можно использовать как постановку задачи: собрать каркас, промпты, схемы, eval и пример прогона.

Ограничение: в условиях кейса нет URL, ключа и формата API для LLM. Пока организаторы их не прислали, весь код обращается к моделям через один тонкий клиент (`llm/client.py`), чтобы адрес, ключ и имена моделей менялись в `.env` без правок остального кода. Формат API (вероятно OpenAI-совместимый) нужно подтвердить.

---

## 1. Что должен делать мой слой

Вход: профиль компании (строка из CSV) и поток новостей и аналитических материалов банка.
Выход: для каждой пары «компания + значимое событие» одна структурированная карточка инсайта (схема в разделе 4), которую бэкенд отдаёт фронтенду без доработки.

Мой слой отвечает за шесть вещей:

1. Профиль компании в виде признаков для промптов.
2. Разбор новостей: классификация, извлечение фактов, дедупликация.
3. Отбор и ранжирование под конкретную компанию.
4. Интерпретация события: риски, возможности, действия, позиция банка.
5. Агентный цикл: план, инструменты, контекст, самопроверка.
6. Контроль качества и расходов: eval, трассировка, кэш, бюджет.

## 2. Жёсткие ограничения из кейса

- Разрешены только модели: Gemma 4 26B A4B, GLM-5.3-Flash, Qwen3.6 35B A3B, DeepSeek-V4.1-Flash, Qwen3-VL-30B-A3B-Instruct, Kimi-K2.6. Любые другие LLM нельзя.
- Нельзя использовать внешние AI-сервисы, автономных агентов и готовые мультиагентные системы как основу. Логику поиска, ранжирования и выводов пишем сами.
- Общий ключ на команду, дневной лимит 500 руб. Расход нужно считать и логировать.
- Результат не должен быть пересказом новости. Ценность в интерпретации с учётом профиля клиента.
- Аналитика Альфа-Банка должна заметно влиять на выводы. Пользователь должен видеть, что мнение банка, а что вывод модели.
- Нужна корректная работа с неполными, неоднозначными и зашумлёнными данными.
- Нужна безопасность AI-компонентов: права доступа, защита чувствительных данных, журнал обращений к инструментам, ограничение опасных действий. Для прототипа достаточно описать и показать место в архитектуре.
- Данные обезличены. Идентификаторы нельзя использовать для установления реальных организаций.

## 4. Контракт данных между слоями

Схему согласовать с бэкендом и фронтом в первый день. Все этапы пайплайна обмениваются JSON, валидируются pydantic-моделями.

### 4.1 Профиль компании (`CompanyProfile`)

```json
{
  "company_id": "U_000123",
  "industry": {"okved_code": "46.71", "okved_name": "Торговля оптовая топливом", "sector_tags": ["топливо", "опт", "логистика"]},
  "size": {"revenue_rub": 18200000000, "revenue_band": "15-30 млрд", "workers_band": "500-1000"},
  "geo": {"city": "Самара", "region": "Самарская область", "foreign_trade": true, "fts_country": "Казахстан"},
  "bank_products": {"loan": true, "leasing": false, "factoring": true, "deposit": true, "guarantee": false, "rko": true, "payroll": true},
  "group": {"group_id": "G_77", "group_size": 4},
  "network": {"top_counterparties": [{"id": "U_000555", "role": "payer", "amt_rub": 420000000, "cnt": 310}], "counterparty_sectors": ["нефтепереработка"]},
  "data_quality": {"missing_fields": ["AMOUNT_WORKERS_SPARK_GRADATION"], "conflicts": []}
}
```

Правило: пропуски и конфликты явно перечислены в `data_quality`. Модель не додумывает отсутствующие признаки.

### 4.2 Разобранная новость (`ParsedItem`)

```json
{
  "item_id": "n_2026_09_11_cbr_rate",
  "source": {"type": "news", "url": "...", "published_at": "2026-09-11"},
  "title": "...",
  "event_type": "monetary_policy",
  "sectors": ["банки", "все отрасли"],
  "regions": ["РФ"],
  "facts": [{"text": "Совет директоров Банка России сохранил ключевую ставку на уровне 14%", "span": "...", "confidence": "confirmed"}],
  "assumptions": [],
  "dedup_cluster": "c_91"
}
```

`confidence` принимает значения `confirmed` и `assumption`. Это нужно, чтобы в карточке отделять факты от предположений.

### 4.3 Карточка инсайта (`InsightCard`), главный результат

```json
{
  "card_id": "ins_U_000123_n_2026_09_11_cbr_rate",
  "company_id": "U_000123",
  "item_ids": ["n_2026_09_11_cbr_rate"],
  "relevance": {"score": 0.86, "reasons": ["у компании есть кредитные продукты", "высокая доля заёмного финансирования инвестиций"]},
  "what_happened": {"text": "...", "facts": ["f1", "f2"]},
  "why_it_matters": {"text": "...", "company_features_used": ["bank_products.loan", "industry.okved_name"]},
  "consequences": {
    "risks": [{"text": "...", "horizon": "6-12 мес", "evidence": ["src_bank_1"]}],
    "opportunities": [{"text": "...", "horizon": "3-6 мес", "evidence": ["src_news_1"]}]
  },
  "bank_view": {"text": "...", "source_ids": ["src_bank_1"]},
  "ai_inference": {"text": "...", "source_ids": ["src_news_1", "profile"]},
  "suggested_actions": [{"text": "...", "type": "action"}, {"text": "...", "type": "question_for_analysis"}],
  "sources": [{"id": "src_bank_1", "kind": "bank_analytics", "title": "Ключевая ставка ЦБ РФ: ставка без изменения на 14,0%, риторика стала жестче", "url": null, "quote": "..."}],
  "limitations": ["Нет данных о доле валютной выручки"],
  "trace_id": "tr_8f2c"
}
```

Правила поля:

- `bank_view` заполняется только из материалов банка с `source_ids`. Если подходящего материала нет, поле равно `null`, а не придумывается.
- `ai_inference` помечается как вывод модели.
- В `facts` только то, что подтверждено источником.
- Каждый элемент `risks`, `opportunities` и каждое `suggested_actions` содержит `evidence` либо явную пометку, что это вывод модели.

## 5. Архитектура пайплайна

Один агент-оркестратор с инструментами. Мультиагентность нужна только там, где она оправдана разделением ролей. Для прототипа достаточно четырёх ролей в одном процессе.

```
[Новости + аналитика банка]
      |
      v
  Ingest/Parse  --> ParsedItem  (Gemma, дёшево)
      |
      v
  Индекс (эмбеддинги/BM25) + RAG по аналитике банка
      |
CompanyProfile --> Ranker (эвристики + эмбеддинги, LLM только для топ-N)
      |
      v
  Orchestrator (plan -> tools -> context -> self-check -> retry)
      |-- tool: get_company_profile
      |-- tool: search_news
      |-- tool: search_bank_analytics (RAG)
      |-- tool: get_counterparty_network
      |-- tool: compute_exposure (риск по связям и продуктам)
      v
  Interpreter (сложная модель) --> InsightCard
      |
      v
  Verifier (проверка источников, противоречий, схемы) --> ok / retry с правкой
      |
      v
  Кэш + трассировка + учёт расходов
```

### 5.1 Эмбеддинги (локальный сервер)

Локальные модели эмбеддингов использовать можно: это не генеративные LLM и не расходует дневной лимит 500 руб. Ограничение «только модели из списка» относится к LLM. Для страховки зафиксировать это в README и `THIRD_PARTY_NOTICES` (модель, версия, источник весов) и при возможности получить подтверждение организаторов письменно.

Рекомендации:

- Для русского текста брать мультиязычную модель семейства e5 (например `multilingual-e5-large` или `-base`, если нужна скорость). Подтвердить на eval, какая даёт лучшие метрики.
- e5 требует префиксы: `query: ...` для запроса (профиль компании, вопрос пользователя) и `passage: ...` для документа (новость, фрагмент аналитики). Без префиксов качество заметно падает.
- Эмбеддинги нормализовать, сходство считать косинусом.
- Тексты длиннее окна модели резать на фрагменты с перекрытием, у каждого фрагмента хранить `source_id`, чтобы RAG возвращал ссылку на первоисточник.
- Запрос от профиля компании собирать из текстовых признаков (отрасль, продукты, регион, контрагенты), а не из сырых полей CSV.
- Схема поиска: гибрид BM25 + e5 (слияние рангов), затем при необходимости реранкинг LLM только для топ-N. Это даёт и качество, и экономию бюджета.
- Сервер эмбеддингов вызывается через `retrieval/embedder.py` с URL из `.env`. Кэшировать эмбеддинги документов на диск, пересчитывать только новые.
- В README указать, что сервер должен быть доступен жюри: поднять в Docker (`docker compose`) вместе с остальными компонентами или дать запасной путь с моделью на CPU, иначе решение не запустится у экспертов.

Метрики для замера вклада: recall@k и nDCG@k ранжирования на размеченных парах «профиль-новость» из eval-набора, сравнение «только BM25», «только e5», «гибрид».

### Агентный цикл (требования кейса)

1. **Планирование.** Оркестратор по профилю и событию решает, какие данные нужны, и записывает план (список шагов) в трассу.
2. **Инструменты.** Вызовы только через реестр инструментов с логированием входов и выходов.
3. **Контекст.** Результаты шагов копятся в одном `RunContext`. Следующие шаги читают его, а не пересобирают заново.
4. **Самопроверка и адаптация.** Verifier проверяет: каждое утверждение имеет источник, нет противоречий между `bank_view` и `ai_inference`, схема валидна, нет общих фраз без привязки к профилю. При провале оркестратор повторяет поиск, уточняет данные или правит конкретный шаг. Лимит повторов 2.

### Маршрутизация моделей (подстроить после замеров)

| Задача | Модель | Почему |
|---|---|---|
| Классификация, извлечение фактов, простые преобразования | Gemma 4 26B A4B | указана в кейсе для задач невысокой сложности, дёшево |
| Интерпретация, рассуждения о последствиях | GLM-5.3-Flash | указана для задач повышенной сложности |
| Универсальные генерации, запасной вариант | Qwen3.6 35B A3B | широкий спектр задач |
| Поиск взаимосвязей, большие объёмы текста | DeepSeek-V4.1-Flash | исследовательские задачи |
| Текстовая обработка | Kimi-K2.6 | задачи по тексту |
| Изображения | Qwen3-VL-30B-A3B-Instruct | нужна только если в источниках есть графики и картинки |

Окончательное распределение определяется замером качества и стоимости на eval-наборе.

## 6. Промпты

Хранить в `prompts/` как отдельные файлы с версиями. В коде только загрузка и подстановка переменных. Каждый промпт требует ответ строго по JSON-схеме, `temperature` 0 для извлечения и классификации, не выше 0.3 для интерпретации.

Файлы:

- `prompts/parse_item.md`: извлечение фактов и классификация. Требует разделять `confirmed` и `assumption`.
- `prompts/relevance.md`: оценка релевантности по признакам профиля, с причинами.
- `prompts/interpret.md`: главный промпт, шесть вопросов из кейса.
- `prompts/verify.md`: проверка карточки и список найденных проблем.
- `prompts/followup_qa.md`: ответ на уточняющий вопрос пользователя по готовой карточке и источникам.

### Скелет `interpret.md`

```
Роль: аналитик для руководителя крупной компании.
Задача: объяснить, как событие повлияет именно на эту компанию.

Дано:
- Профиль компании: {company_profile_json}
- Факты события: {parsed_item_json}
- Материалы аналитики банка (фрагменты с id): {bank_chunks}
- Результаты предыдущих шагов: {run_context}

Правила:
1. Не пересказывай новость. Объясни последствия для этой компании.
2. Используй конкретные признаки профиля (укажи какие в company_features_used).
3. Каждое утверждение в bank_view опирай на фрагмент банка и укажи его id.
   Если подходящего фрагмента нет, bank_view = null.
4. Выводы, сделанные тобой, помещай только в ai_inference.
5. Не придумывай цифры и признаки, которых нет в профиле. Нехватку данных
   перечисли в limitations.
6. Предложи действия и вопросы для дополнительного анализа, привязанные к профилю.
7. Ответ строго JSON по схеме InsightCard.
```

## 7. Эталонный пример (ориентир по качеству)

Профиль: компания с кредитными продуктами, часть инвестиций финансируется заёмными средствами.
Событие: ключевая ставка сохранена на 14%.

Плохо (пересказ, из примера в кейсе):

> 11 сентября 2026 года совет директоров Банка России принял решение сохранить ключевую ставку на уровне 14% годовых. Это первая пауза в цикле смягчения денежно-кредитной политики после десяти последовательных снижений ставки, начавшегося в июне 2025 года.

Хорошо (целевой уровень; тексты банка ниже условные, настоящие брать только из выданных материалов):

```json
{
  "relevance": {"score": 0.9, "reasons": ["есть кредитные продукты", "инвестиции частично за счёт заёмных средств"]},
  "what_happened": {"text": "Банк России сохранил ключевую ставку на уровне 14% после серии снижений. Решение принято 11 сентября 2026."},
  "why_it_matters": {"text": "Кредитная нагрузка компании остаётся высокой: удешевление заёмных денег, на которое мог рассчитывать бизнес, откладывается.", "company_features_used": ["bank_products.loan"]},
  "consequences": {
    "risks": [{"text": "Стоимость обслуживания долга не снизится в ближайшей перспективе; проекты с высокой долей заёмного финансирования дольше окупаются.", "horizon": "6-12 мес", "evidence": ["src_bank_rate"]}],
    "opportunities": [{"text": "Свободную ликвидность выгоднее размещать на депозитах при сохранении высокой ставки.", "horizon": "3-6 мес", "evidence": ["profile"]}]
  },
  "bank_view": {"text": "По оценке аналитиков банка, риторика регулятора стала жестче, что снижает вероятность быстрого возобновления снижения ставки.", "source_ids": ["src_bank_rate"]},
  "ai_inference": {"text": "Для компании с кредитами разумно пересмотреть график заимствований и приоритизировать проекты по окупаемости.", "source_ids": ["profile", "src_bank_rate"]},
  "suggested_actions": [
    {"type": "action", "text": "Проверить условия рефинансирования действующих кредитов."},
    {"type": "question_for_analysis", "text": "Какая доля инвестпрограммы на следующий год зависит от заёмного финансирования?"}
  ],
  "limitations": ["Нет данных о валютной структуре долга"]
}
```

Признаки хорошей карточки: она называет конкретные признаки компании, различает «банк считает» и «модель предполагает», у каждого вывода есть источник, действия не общие, ограничения данных названы.

## 8. Eval и мониторинг

Критерий кейса: стабильное качество на новостях, которых не было в демо, и процесс регулярного мониторинга.

Eval-набор (`eval/`):

- 20-30 профилей компаний, разные отрасли и размеры, плюс несколько с пропусками и конфликтами в данных.
- 30-50 новостей и материалов, включая нерелевантные, дубликаты, противоречащие друг другу и «зашумлённые» тексты.
- Синтетические, без реальных данных.

Метрики:

| Метрика | Как считать |
|---|---|
| Валидность схемы | доля карточек, прошедших pydantic |
| Покрытие источниками | доля утверждений с непустым `evidence` |
| Фактологичность | выборочная ручная проверка и LLM-судья на другой модели |
| Персонализация | доля карточек, где `company_features_used` непусто и реально влияет на текст |
| Разделение банк/ИИ | нет `bank_view` без `source_ids` |
| Отсев нерелевантного | precision и recall ранжирования на размеченных парах |
| Устойчивость | качество на «чистом» наборе против зашумлённого |
| Стоимость | токены и руб. на карточку, суммарно за день |
| Латентность | время на карточку |

Мониторинг: каждый запуск пишет трассу (`trace_id`): план, вызовы инструментов, использованные источники, промежуточные результаты, число повторов, стоимость. Обратная связь пользователей и экспертов (палец вверх/вниз, комментарий) сохраняется и идёт в eval-набор.

## 9. Бюджет и кэш (500 руб. в день на команду)

- Предрасчёт: разбор новостей и фрагментов аналитики делается один раз при загрузке и кэшируется.
- Кэш по ключу `hash(item_id, company_profile_hash, prompt_version, model)`.
- Дешёвая модель для массовых шагов, дорогая только для интерпретации топ-N.
- Эвристики и эмбеддинги (локальный сервер e5, см. раздел 5.1) для первичного отсева до обращения к LLM.
- Счётчик расходов в клиенте: считает токены, оценивает рубли, останавливает запуск при приближении к лимиту, пишет в лог.
- Для отладки использовать малые выборки.

## 10. Безопасность AI-слоя

- Реестр инструментов с белым списком. Инструменты только на чтение, опасных действий нет.
- Модель получает только данные нужной ей компании, а не весь CSV (разграничение доступа).
- Данные уже обезличены. Не пытаться и не позволять модели устанавливать реальные организации по идентификаторам.
- Тексты новостей и аналитики это недоверенные данные: в промптах разделять инструкции и данные, не исполнять команды из текста источников (защита от prompt injection).
- Журнал всех обращений к инструментам и LLM.
- Секреты только в `.env`, файл в `.gitignore`.

## 12. Критерии готовности моей работы

- [ ] Клиент LLM работает через `.env`, разрешены только модели из списка кейса.
- [ ] Для любой компании из CSV строится `CompanyProfile` с явным `data_quality`.
- [ ] Для любой новости строится `ParsedItem`, дубликаты схлопываются.
- [ ] Ранжирование отдаёт ленту под компанию, нерелевантное отсеивается.
- [ ] `InsightCard` проходит валидацию схемы в 100% запусков (с ретраем).
- [ ] В каждой карточке разделены `bank_view` и `ai_inference`, у утверждений есть источники.
- [ ] Агентный цикл показывает план, вызовы инструментов, самопроверку и хотя бы один реальный ретрай в трассе.
- [ ] Работает на новостях, которых нет в демо-наборе.
- [ ] Есть ответ на уточняющий вопрос по карточке со ссылкой на первоисточник.
- [ ] Есть eval-набор, метрики и отчёт `eval/report.md`.
- [ ] Расход за прогон eval укладывается в дневной лимит, это подтверждается логом.
- [ ] Промпты версионированы, README описывает пайплайн и выбор моделей.
- [ ] Схемы согласованы с бэкендом и фронтом и не менялись в последний день.
