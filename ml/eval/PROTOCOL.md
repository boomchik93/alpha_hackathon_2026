# Протокол оценки

Цель: метрики должны показывать, как решение работает на новых компаниях и отраслях, а не на тех, под которые его настраивали.

## Наборы

| Набор | Состав | Эталон | Команда |
|---|---|---|---|
| v1 | 9 компаний (`companies.json`) x 19 новостей + 9 документов банка | ручной (`labels.py`) | `python -m ml.eval.run_eval` |
| v2 | 40 компаний и групп (`companies_v2.json`): dev 20, test 20 | ручной для 9 исходных, для остальных согласие двух LLM (`labels.jsonl`) | `python -m ml.eval.run_eval --set v2` |

v2 собирается так:
1. `python -m ml.eval.sample`: стратифицированная выборка по стратам ОКВЭД (2 цифры, для опта 3), seed фиксирован. dev: страты исходных 9 компаний плюс случайная половина остальных; test: другая половина. Компании одной страты всегда в одной части.
2. `python -m ml.eval.label_llm`: разметка 0/1/2 двумя моделями (DeepSeek, Qwen) по `prompts/label_relevance.md`. Совпало: `llm_agreed`; разошлось: `llm_disputed`, идёт в `review_labels.md` на ручную проверку и в метрики не входит, пока не проверено.
3. `python -m ml.eval.sample --pairs`: 300 фиксированных пар «компания x новость» для карточек: 240 релевантных и 60 нерелевантных, поровну dev и test.

## Что можно и что нельзя

На dev можно: подбирать параметры ранжирования, менять промпты, смотреть карточки и ошибки.

На test нельзя:
- подбирать параметры и пороги (подбор в `eval_ranking_cv` идёт только на dev);
- разбирать отдельные карточки test, чтобы чинить промпт под них;
- добавлять правила под отрасли test.

Test смотрится только как итоговая цифра в отчёте. Если test пришлось разобрать (например, нашёлся баг пайплайна), это записывается в `analysis.md`. После этого test считается использованным, и для следующей итоговой оценки нужна новая выборка (сменить `SEED` в `sample.py`).

Holdout-новости (`holdout_news.jsonl`) при настройке промптов не читаются.

**Оговорка (ревью 2026-10-21).** Фактически отложенные новости v1 (`holdout_news.jsonl`, id `h_*`) использовались при настройке ленты: правила введены под три из них (`h_2026_09_08_pharma`: смежность 47.73 → 46.46; `h_2026_09_09_housing`: ключи «застройщ/новострой/девелоп/ипотек» и смежность стройки; `h_2026_09_10_grain_duty`: `OFF_SECTOR_DAMP`). Поэтому в отчётах срез называется «отложенные v1 (использовались при настройке ленты)» и не считается доказательством устойчивости на ранее не показанных новостях. Split test даёт новые компании, но те же 26 материалов, и все 19 новостей синтетические.

## holdout2: настоящий отложенный набор новостей

Набор `ml/eval/holdout2_news.jsonl` собирает `python -m ml.eval.collect_holdout2` (RSS из `NEWS_RSS_URLS`, фиксированный seed), хэш файла, дата сбора, `as_of` и источники пишутся в `ml/eval/holdout2.lock`. Правила:
- после заморозки (появления lock-файла) содержимое holdout2 не читается и не размечается до итоговой оценки;
- на нём не подбираются параметры ленты, промпты и пороги;
- использовать один раз; если найден баг пайплайна, он записывается в `analysis.md`, и для следующей итоговой оценки нужен holdout3.

## Что публикуется

- Метрики dev и test отдельно, разрыв dev − test. Цель по nDCG@5: разрыв не больше 0,05.
- 95% интервалы bootstrap по компаниям (лента) и по парам (карточки).
- Метрики ленты отдельно по ручному эталону (v1) и по ручному + согласованному (v2).
- Оценки обоих судей и их согласие. Если согласие низкое, разница между прогонами меньше расхождения судей не считается эффектом.
- Любой подбор параметров записывается в `analysis.md` с указанием данных, на которых он делался.

## Известные ограничения

- Инструкция разметки v2 уточнялась по согласию с ручной разметкой на тех же 9 компаниях (dev). Согласие с человеком на них (κ_w 0,81) поэтому завышено. На test оно не измерено: нужна ручная выборка.
- Судьи: LLM, другие семейства, чем интерпретатор (GLM). Их ошибка измеряется только ручной калибровкой (`review_judges.md`).

## real и real2: реальные новости (2026-10-22)

- `real` (`real_news.jsonl`, 79 новостей 16–22.10): holdout (20–22.10) использован при выборе режима причин, поэтому весь
  набор — данные разработки. Модель пары ленты (`ml/ranking/pair_model.py`) выбирается перекрёстной проверкой
  «без одного дня» по 7 дням real с ограничениями по v2 и по 9 компаниям с ручной разметкой, и обучается на всём real и v2.
- `real2`: настоящий отложенный набор. Записи лент копятся в `real_pool.jsonl` ежедневно (`make real-pool`, RSS хранит
  записи несколько дней); набор замораживается из пула за дни после 22.10 (`make real2-freeze START=... ASOF=...`),
  размечается (`make real2-label`) и оценивается один раз (`make real2-eval`, `ml/eval/final_eval.py`: прежняя лента,
  правила, модель+правила, парный bootstrap). До оценки пул и real2 не читаются; параметры после оценки не меняются,
  иначе для следующей итоговой цифры нужен real3.
- Карточки на реальных новостях: только пары dev из `card_pairs_real.json` (`python -m ml.eval.card_pairs_real`, выбраны
  до генерации из пар, которые показывала лента).

## Двухуровневая лента: точка, объявленная до заморозки real2 (2026-10-23)

Записано до заморозки real2 (`ml/eval/real2_news.lock` ещё нет), закоммичено, чтобы дата была видна в истории.

- Пороги по личному скору пары (`ranker.MAIN_SCORE`, `ranker.MIN_SCORE`):
  - основная лента (`tier=main`): от **0,40**, плюс любое событие прямо в отрасли компании (совпадение ОКВЭД);
  - блок «может быть интересно» (`tier=maybe`): от **0,30** до 0,40;
  - ниже 0,30: отсев.
- Макрособытие без зацепки в профиле, прошедшее отсев только по полу `ECONOMY_MIN_IMPORTANCE` (личный скор ниже 0,40): `maybe`
  (`ML_FEED_MACRO_TIER=maybe`).
- Главная метрика: точность основной ленты против ручной разметки (пары `source=human`). Ограничение: полнота основной ленты
  вместе с блоком «может быть» против ручной разметки.
- Критерий успеха на real2: точность основной ленты не ниже **60%** при полноте обоих уровней не ниже **80%**. Ориентиры на
  210 ручных парах real (dev, внефолдово): 67% и 86%; на этих же парах 0,40 подбирался, поэтому они завышены.
- Остальные метрики (F0.5, precision@5, доля нужного в «может быть», парный bootstrap против прежней ленты) публикуются,
  но решение по ним не принимается.
- Ручная разметка real2 (150 случайных пар, тот же чек-лист `label_review_real.CRITERIA`) делается до просмотра результатов
  ленты на real2. Оценки лент в файл для разметки не попадают.
- После просмотра результатов real2 пороги не меняются. Если поменяли, итоговая проверка проводится на следующем наборе (real3).
- До заморозки real2 порог можно менять по результатам проверки на данных разработки (этап 4 плана); изменение записывается
  в `ml/eval/analysis.md` с данными, на которых оно сделано, и в этот раздел.
