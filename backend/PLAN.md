# План работы бэкендера

Составлен по условиям кейса «Альфа Хак. Новостная аналитика для принятия бизнес-решений» (PDF кейса, [ml/docs/ML_SPEC.md](../ml/docs/ML_SPEC.md), [ml/docs/PLAN.md](../ml/docs/PLAN.md)) и текущему контракту ML-сервиса ([ml/server.py](../ml/server.py), [ml/schemas.py](../ml/schemas.py)). ML-пайплайн не меняем. Крайний срок хакатона в материалах не указан: порядок P1 и P2 подгоняется под него. План фронтенда: [frontend/plan.md](../frontend/plan.md).

## Что от бэкенда требует кейс

Номера в скобках: критерии успеха (К01–К12) и ограничения (О01–О06) из PDF кейса.

- API для фронта: компании, профиль, лента, карточка, уточняющий вопрос, обратная связь (К06, К10).
- Сервис для людей, а не для юрлиц: у одной компании несколько пользователей с разными ролями. Роль влияет на акцент карточки (раздел «Целевая аудитория»).
- Точка входа на главном экране интернет-банка (К09): фронту нужна лёгкая ручка-сводка для виджета (сколько новых важных событий, главное из них).
- Данные «в другом разрезе» и переход к первоисточнику (К10): фильтры ленты, переключение компания / группа, отдача страницы PDF аналитики банка по ссылке из карточки.
- Трассируемость (К12): по карточке можно восстановить источники, признаки компании и промежуточные шаги агента. Жюри должно увидеть это в интерфейсе.
- Устойчивость на новых новостях (К05): лента не должна быть статичной, новости обновляются по расписанию, а не только из фикстур.
- Мониторинг с обратной связью пользователей и экспертов (К08): трассы, оценки, расход.
- Хранение того, чего нет в файлах ML: пользователи, история просмотров, обратная связь.
- Прокси к ML (`:8001`) с понятными ошибками для фронта.
- Безопасность AI-слоя (О06): права доступа, защита данных, журнал обращений, ограничение опасных действий. Для прототипа достаточно описать и показать место в архитектуре.
- Комплект сдачи: Docker и единый способ запуска, README, lock-файлы, `THIRD_PARTY_NOTICES`, синтетические данные и тестовые учётные записи для сквозного сценария, по желанию OpenAPI и модель данных. Живой деплой на бесплатном сервере, доступный жюри.
- Бюджет моделей 500 руб. в день на всю команду (О04): бэкенд не должен бесконтрольно запускать платные вызовы.

## Что уже есть в ML-сервисе

- Ручки: `/companies`, `/companies/{id}`, `/companies/{id}/feed?tier=all|main&limit&maybe_limit`, `/companies/{id}/insights/{item_id}?refresh&role`, `POST /cards/{id}/followup?role`, `POST /cards/{id}/feedback`, `/feedback/summary`, `/traces/{id}`, `/health`.
- Роли: `owner/ceo/cfo/treasurer/chief_accountant/other` ([ml/roles.py](../ml/roles.py)). Карточка для разных ролей получает разный `card_id`.
- Ошибки ML: 404 нет объекта, 429 исчерпан бюджет, 502 модель не дала годный ответ.
- Карточка при первом запросе генерируется около 15 секунд (p95 около 31 секунды), потом отдаётся из кэша. Предрасчёт: `python -m ml.precompute --companies demo --top 3`.
- Обратная связь уже пишется в `var/feedback.jsonl` внутри ML, со сводкой по версии промпта. Причины «не полезно»: `wrong_fact`, `not_relevant`, `obvious`, `other`.

## Чего не хватает и что учесть

- В `ml/server.py` нет авторизации и CORS: наружу выставляем только бэкенд.
- `/traces/{id}` отдаёт всю трассу: наружу только через бэкенд, с ролями (см. п. 17).
- Генерация синхронная и длинная: нужны фоновая задача и состояние «генерируется». Бесплатные хостинги и прокси часто рвут запрос на 30–60 секундах, поэтому долгий синхронный запрос ненадёжен.
- Лента двухуровневая (`tier`, `maybe_count`): сообщить фронту про блок «может быть интересно».
- `FeedEntry` содержит только заголовок, дату, оценку, причины и темы. Для ленты нужны краткое содержание и ссылка на источник (кейс: «показать, что содержится в новостях»). Согласовать с ML поля `summary` и `url` в `FeedEntry` или ручку `/items/{item_id}`.
- В ML нет ручки сбора новостей: обновление идёт командами (`make real-pool`, сборка `items`). Нужен запуск по расписанию и время последнего обновления в ответе ленты.
- Страницы PDF аналитики уже есть картинками в `data/analytics_pages/`: их можно отдавать по `doc_id` и `page` из `SourceRef`.
- `data/` и `var/` в репозиторий не входят: получить у владельца ML для деплоя.

## P0. Скелет и сквозной сценарий

1. Выбрать стек и записать в `backend/README.md`. Рекомендация: FastAPI (тот же язык, что у ML, OpenAPI для фронта из коробки), SQLite, при необходимости Postgres.
2. Поднять ML (`LLM_MOCK=1`), пройти все ручки руками, сохранить реальные примеры ответов для фронта (фронт использует их как моки).
3. Сделать API для фронта: прокси к ML с пагинацией. Формат ответов не менять без согласования с ML и фронтом.
4. Единый формат ошибок `{code, message, retry_after?}`:
   - 404: объект не найден;
   - 403: нет доступа к компании;
   - 429: «лимит расходов исчерпан, показаны сохранённые карточки»;
   - 502: «модель не справилась, повторите»;
   - 504: таймаут ML.
5. Включить CORS для фронта. В деплое лучше отдавать фронт и API с одного домена через прокси, тогда CORS не нужен.
6. Скрипт или ручка для предрасчёта карточек демо-компаний (для всех демо-ролей, если роль меняет карточку).
7. Роль пользователя из его профиля передавать в ML (`role` в карточке и уточняющем вопросе). Фронт роль не передаёт, бэкенд берёт её из сессии.

## P0. Генерация карточки без зависания фронта

8. Для не предрассчитанной карточки: `202` с `job_id`, фоновая задача, опрос `GET /jobs/{id}` раз в 1–2 секунды (статусы `queued/running/done/failed`). Готовая карточка из кэша отдаётся сразу `200`. Решение согласовать с фронтендером в первый день.
9. Ограничить число одновременных генераций.
10. Дедуплицировать параллельные запросы одной тройки «компания + новость + роль».
11. Параметр `refresh=true` пользователям не открывать: он тратит деньги.

## P0. Хранение

12. Таблицы: пользователи, привязка пользователя к компании или группе, роль (`owner/ceo/cfo/treasurer/chief_accountant/other`) и тип доступа (`user/expert/admin`), история просмотров, обратная связь.
13. Обратную связь писать в БД и дублировать в ML через `POST /cards/{id}/feedback` (с ролью), иначе сломается сводка по версии промпта.
14. История просмотров даёт признак «новое» в ленте и счётчик для виджета главного экрана.

## P0. Ручки под критерии интерфейса

15. `GET /me/summary`: число новых материалов основной ленты, главный материал (заголовок, оценка, дата), время обновления ленты. Только данные ленты, без генерации карточек. Нужна для виджета на главном экране (К09).
16. Фильтры ленты (К10): уровень (`main/maybe`), тип источника (`news/bank_analytics`), тема, период, скрывать устаревшие. Фильтровать на бэкенде поверх ответа ML. Для группы: переключатель «компания / группа» по `member_ids` и `level`.
17. Трассы (К11, К12): `GET /cards/{id}/trace`. Пользователь видит упрощённый вид: план, вызванные инструменты, повторы, использованные источники и признаки профиля. Эксперт и админ видят полную трассу с расходом. Сырые промпты и ответы модели обычным пользователям не отдавать.
18. Первоисточник (К10): `GET /sources/{doc_id}/pages/{page}` отдаёт картинку страницы аналитики банка из `data/analytics_pages/`. Проверять, что `doc_id` есть в белом списке документов, без путей из запроса.

## P1. Безопасность и защита бюджета

19. Авторизация: токен или сессия. Для демо хватит тестовых учётных записей (несколько ролей на одну компанию, один эксперт, один админ); логины перечислить в README, пароли в сиде, не в коде.
20. Проверка доступа: пользователь видит только свои компании. ML ограничивает агента одной компанией, бэкенд добавляет такую же границу на уровне API. Демо-переключатель «выбрать любую компанию» только у эксперта и админа.
21. Лимиты частоты на уточняющие вопросы и генерацию карточек; длина вопроса не больше 500 символов, как в ML.
22. Журнал обращений: кто, какую компанию и карточку открыл, какой вопрос задал, какой `trace_id`.
23. Ключи и пароли только в `.env`; LLM-ключ фронту не отдавать.
24. Данные обезличены, идентификаторы не расшифровывать; отразить в описании безопасности. В описании показать место каждого механизма в архитектуре (схема в README).

## P1. Обновление новостей

25. Задача по расписанию (отдельный сервис в compose или cron в контейнере ML): сбор RSS и сборка `items`, затем сброс кэша ленты. Режим «только фикстуры» включается одной переменной для детерминированного демо.
26. Время последнего обновления и число новых материалов отдавать в ленте и `/me/summary`.

## P1. Мониторинг

27. Ручка статуса: `/health` ML, расход за день и бюджет, доля `down` из `/feedback/summary` по ролям и причинам.
28. Экспертная оценка (К08): эксперт ставит оценку карточке тем же способом, что пользователь, но с типом `expert`; сводка показывает обе группы отдельно.
29. Простая админ-страница или JSON со сводкой для презентации.
30. Структурные логи с `request_id` и `trace_id`.

## P1. Деплой

31. `backend/Dockerfile`; в `docker-compose.yml` добавить `backend` и `frontend` рядом с `ml`, общий том `var/`, `data/` только для чтения. Один `docker compose up` поднимает всё.
32. Живой деплой на бесплатном сервере, доступный жюри; передать фронту URL и порядок переменных.
33. Проверить: без `LLM_BASE_URL` стартует на моке, с ключом работает на реальных моделях.
34. Зафиксировать зависимости (lock-файл), дописать `THIRD_PARTY_NOTICES.md`.
35. На момент дедлайна поставить тег версии и указать commit hash в README. Если репозиторий приватный, дать доступ аккаунту `alfa-hack-2026`.

## P2. Документация, тесты, демо

36. `backend/README.md`: стек, запуск, тестовые учётные записи, список ручек, схема ошибок, безопасность и масштабирование (stateless-бэкенд, кэш карточек, предрасчёт, очередь генерации, новые отрасли и источники через конфиг ML). Выгрузить OpenAPI в файл.
37. Тесты: контракт с ML на моке; ошибки 404, 403, 429, 502, 504; доступ к чужой компании; лимиты; фоновая генерация и дедупликация.
38. Репетиция демо с фронтом и продуктом: 3-5 демо-компаний, 1-2 «трудных» с пропусками в данных; смена компании и роли меняет ленту и акцент карточки; карточка, уточняющий вопрос, переход к странице PDF, «не полезно», трасса.
39. Резерв на случай падения ML или бюджета: показывать только сохранённые карточки.

## Что согласовать

- С владельцем ML: передать `data/` и `var/`; запуск предрасчёта; поля `summary` и `url` в ленте; запуск сбора новостей по расписанию; будущие изменения формата ответов.
- С фронтом: фоновая генерация и опрос статуса, схема ошибок, фильтры ленты, `/me/summary`, вид трассы для пользователя и эксперта.
- С продуктом: роли и тестовые учётные записи, демо-сценарий, метрики мониторинга.
